# Forwarded bill ingestion

This is a development integration, not a deployed email service. Provision and verify `in.proxic.app` and configure the connector before giving customers addresses. Inbound mail must retain the full envelope recipient, including the case-sensitive token.

Email inbox/connector -> Logic Apps -> private Blob quarantine -> malware scanning -> Azure Function -> BillSubmission -> Bill Parser. The workflow must store every attachment in quarantine before scanning, scan its actual bytes, and wait for a definitive result. Filename and MIME type are descriptive only. Never invoke the parser with unscanned, failed, or malicious content; this implementation does not read attachment bytes at all. The mock parser reads only explicit fields in the email text, not attachments, and only supports USD. Missing or invalid fields are marked `needs_review`; this version does not provide a review UI or retain email text. Preserve the original securely in the mail workflow if later review is needed.

## Trust boundary

The internal `POST /api/internal/bills/ingest` function uses Azure Functions **function-level authentication**, not Firebase. Give the Logic App a dedicated function key in the `x-functions-key` header, stored in Key Vault and accessed with managed identity. Require HTTPS, restrict network ingress to the workflow/private network, rotate the key, and do not expose it to browsers or log it. Azure Functions Core Tools disables key enforcement locally: never expose a local host publicly. The caller is trusted to supply truthful scan results tied to the exact quarantined blob version; do not allow customers to call this endpoint directly or supply scan results. A function key is a shared credential, not proof of scanning. Configure scanner access, blob immutability/versioning and least-privilege access before production. No scanner, Blob client, or email connector is implemented here.

Request JSON contains `recipientAlias`, `sender`, `subject`, UTC `receivedAt`, `textContent`, and `attachments`. Each attachment has `fileName`, `contentType`, `storageReference` (a relative `quarantine/...` object path, without URL or SAS), and `scanStatus` (`pending`, `failed`, `malicious`, or `clean`). Bodies are bounded; binary data and extra fields are rejected. Only the alias determines the owner. Unknown/revoked aliases return 404. Pending or failed scans create quarantined submissions; malicious scans create rejected submissions; all return 422 and no parser is called. Clean or attachment-free requests return 201 with a submission ID and status. Reposting after a scan creates a separate submission; there is no scan-update or delivery-idempotency API yet. Bills are deduplicated per owner by normalized merchant, amount, currency, due date, and optional last four; last four alone is never an identifier.

No payment provider is called. Complete bills create an approval-required proposal; ingestion never approves or executes a payment. Audit records omit email contents, addresses, tokens, blob paths, and financial details. Do not log request bodies, authorization headers, connector secrets, or function keys in Azure diagnostics.

## Alias key and deployment

Set `FORWARDING_ALIAS_ENCRYPTION_KEY` to an independent, securely generated 32-byte hex key using Azure configuration/Key Vault. The random 256-bit token is hashed for lookup and encrypted with AES-256-GCM for authenticated redisplay; no plaintext token is stored. Back up the key securely: losing or changing it makes existing addresses impossible to display; rotate/reissue aliases using a planned key migration. Rotation immediately revokes the old address, including in-flight messages not yet ingested. Applying the migration revokes any pre-existing legacy aliases and removes their plaintext values.

Apply database migrations before deploying the functions. The partial unique index serializes the active alias invariant; PostgreSQL row/advisory locks coordinate ingestion with rotation. Use an isolated test database and `TEST_DATABASE_URL` to run the integration tests.
